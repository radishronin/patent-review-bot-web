# OA Response Builder — Claims Builder Extension
## Build primer for Fable (Code tab)

You are extending an existing single-file offline tool, `OA_Response_Builder.html`, to add an
in-app **Claims Builder**. Read this whole primer before touching the file. It contains the
format spec, the data model, the render rules, reference implementations for the small pure
functions, the exact hook points in the current file, and a golden example to test against.
The goal is to spend your budget on implementation, not on rediscovering the file.

---

## 0. Hard constraints (do not violate)

1. **Edit the file in place.** Do not scaffold a new project, do not split into modules, do not
   introduce a build step, do not add dependencies. The tool ships as one offline HTML file and
   must stay that way ("nothing leaves this file" is a feature).
2. **Reuse the embedded template and styles.** The `.docx` is produced by injecting OOXML
   paragraphs into a base64-embedded copy of the firm template (`BASE64_DOCX`) via JSZip. The
   caption, `styles.xml` (styles `OASubheader`, `BodyText`, `TitleStyle`, `OABlockQuote`, etc.),
   spacing, and margins are firm-perfect. **Never regenerate the docx machinery and never restyle
   anything.** Your new code emits runs/paragraphs through the *existing* helpers only.
3. **All markup is manual.** These are manual underline/strikethrough amendments under 37 CFR
   1.121, never Word tracked-changes. No `<w:ins>` / `<w:del>` revision elements. Insertions are
   run-level `<w:u w:val="single"/>`; deletions are run-level `<w:strike/>`.
4. **Additive UI.** Add a Claims Builder panel; leave every existing field and section working.

## 1. The interchange format (plaintext)

One human-readable, hand-editable, copy-pasteable block. It is authored either by the attorney
directly in the tool or generated by the Reasoner (Claude) and pasted in. Same format either way.

### Grammar

```
%% <num> [directive]...
<body line>
<body line>
...
%% <num> [directive]...
...
```

- A line beginning with `%%` is a **claim header**. Body lines never begin with `%%`.
- Header = `%%`, whitespace, the claim number, then zero or more space-separated **directives**.
- Directives (any order): `cancel`, `withdraw`, `new`, `notentered`, `prior`.
  - `cancel` / `withdraw` / `new` / `notentered` set the claim's operation.
  - `prior` means the claim was amended, added, or presented in a **previous** response (needed to
    distinguish Original from Previously Presented when the claim is untouched now).
- Each non-empty line after a header, up to the next header, is one **body paragraph**. Blank
  lines are ignored.
- An empty body is valid (e.g. a canceled claim).
- A line beginning with `;;` is a **note** (antecedent flags, status caveats from the Reasoner). It
  is ignored by the parser **anywhere** in the block and surfaced in the validation strip — never
  rendered into the docx.

### Inline markup (within body lines)

| Syntax            | Meaning                        | Render                         |
|-------------------|--------------------------------|--------------------------------|
| `{+ ... +}`       | insertion                      | underline (`<w:u w:val="single"/>`) |
| `[- ... -]`       | deletion                       | single strikethrough (`<w:strike/>`) |
| `[[ ... ]]`       | short deletion (≤3 chars, optional convention) | literal text **including** the `[[ ]]` brackets, normal weight, no strike |

Edits are always authored against the **currently pending** state of the claims (the text as it
stands from the previous response). Edits never stack (no insertion that is later deleted). The
parser may assume this.

## 2. The claim-status model

The parser converts the interchange block into an ordered map keyed by claim number. This is the
**single source of truth** — both the claims listing and the Status-of-the-Claims ranges derive
from it, so they can never disagree.

```js
// One entry per claim, preserving input order.
{
  num: 8,                     // integer
  op: "amend",               // "amend" | "cancel" | "withdraw" | "new" | "notentered" | "none"
                             //   ("none" and "amend" both mean the claim keeps a body; "amend"
                             //    is set only when edits are present — see computeStatus)
  priorAltered: false,        // true if the `prior` directive was present
  paras: [                    // body split into paragraphs; each paragraph is an array of tokens
    [ {op:"keep", text:"..."}, {op:"ins", text:"..."} ],
    [ {op:"keep", text:"..."} ]
  ],
  hasEdits: true,             // computed: any token in any paragraph is ins | del | dbrak
  status: "Currently Amended",// computed label text (see §3)
  boldLabel: true,            // computed: true only for Currently Amended and New
  keepBody: true              // computed: false only for Canceled
}
```

Token `op` values: `keep`, `ins`, `del`, `dbrak`.

## 3. Status-label computation

All eight identifiers are supported. The label is **computed**, never typed, so it always matches
the claim's actual state.

```js
function computeStatus(c) {
  // c has: directive op (cancel/withdraw/new/notentered/none), priorAltered, hasEdits
  switch (c.rawOp) {
    case "cancel":     return { status: "Canceled",           boldLabel: false, keepBody: false };
    case "withdraw":   return { status: "Withdrawn",          boldLabel: false, keepBody: true  };
    case "new":        return { status: "New",                boldLabel: true,  keepBody: true  };
    case "notentered": return { status: "Not Entered",        boldLabel: false, keepBody: true  };
  }
  if (c.hasEdits)      return { status: "Currently Amended",  boldLabel: true,  keepBody: true  };
  return c.priorAltered
    ? { status: "Previously Presented", boldLabel: false, keepBody: true }
    : { status: "Original",             boldLabel: false, keepBody: true };
}
```

Rules in words:

- **Touched this response** (any inline markup present) → **(Currently Amended)**.
- Directive `cancel` → **(Canceled)**, body dropped.
- Directive `withdraw` → **(Withdrawn)**, body kept (renders like Original/Previously Presented).
- Directive `new` → **(New)**, body kept.
- Directive `notentered` → **(Not Entered)**, body kept (firm has no set convention; we keep the
  proposed body).
- **Untouched now, altered before** (`prior`) → **(Previously Presented)**.
- **Untouched now, never altered** → **(Original)**.

**Bold parenthetical for (Currently Amended) and (New) only.** All other labels render normal weight.

## 4. Render rules (claims listing)

Reuse the **same paragraph style the current verbatim claims path uses** (found at the
`claimsText` insertion point — see §6). Do not invent a style.

**First paragraph of a claim** = number, tab, label, space, then the first body paragraph's runs:

```
run(num + ".")  +  tab()  +  run("(" + status + ")", {b: boldLabel})  +  run(" ")  +  <body runs>
```

**Canceled claims** are label-only, no body:

```
run(num + ".")  +  tab()  +  run("(Canceled)")
```

**Subsequent body paragraphs** of a multi-paragraph claim are their own paragraphs in the claim
style, with body runs only (no number/label prefix).

**Token → run mapping:**

```js
function tokenRun(t) {
  switch (t.op) {
    case "ins":   return run(t.text, { u: true });   // underline
    case "del":   return run(t.text, { s: true });   // strikethrough
    case "dbrak": return run(t.text);                // t.text already includes the [[ ]] brackets
    default:      return run(t.text);                // keep
  }
}
```

## 5. Reference implementations

### 5.1 Extend `run()` — add the strike flag

Current `run()` supports `b` / `i` / `u`. Add `s` (strike). This is the only change to an existing
helper. Insertions must underline; deletions must strike; both must be manual run properties.

```js
function run(text, o) {
  o = o || {};
  let rpr = "";
  if (o.b || o.i || o.u || o.s)
    rpr = "<w:rPr>"
        + (o.b ? "<w:b/>" : "")
        + (o.i ? "<w:i/>" : "")
        + (o.s ? "<w:strike/>" : "")
        + (o.u ? '<w:u w:val="single"/>' : "")
        + "</w:rPr>";
  return "<w:r>" + rpr + '<w:t xml:space="preserve">' + esc(text) + "</w:t></w:r>";
}
```

### 5.2 Inline tokenizer (body line → tokens)

```js
const IX_RE = /\{\+([\s\S]*?)\+\}|\[-([\s\S]*?)-\]|\[\[([\s\S]*?)\]\]/g;

function tokenizeBody(line) {
  const tokens = [];
  let last = 0, m;
  IX_RE.lastIndex = 0;
  while ((m = IX_RE.exec(line)) !== null) {
    if (m.index > last) tokens.push({ op: "keep", text: line.slice(last, m.index) });
    if (m[1] !== undefined)      tokens.push({ op: "ins",   text: m[1] });
    else if (m[2] !== undefined) tokens.push({ op: "del",   text: m[2] });
    else if (m[3] !== undefined) tokens.push({ op: "dbrak", text: "[[" + m[3] + "]]" });
    last = IX_RE.lastIndex;
  }
  if (last < line.length) tokens.push({ op: "keep", text: line.slice(last) });
  return tokens;
}
```

`hasEdits` for a claim = any token across all paragraphs has op `ins`, `del`, or `dbrak`.

### 5.3 Parser (interchange text → model)

```js
function parseInterchange(text) {
  const claims = [];
  const notes = [];                         // ";;" lines, shown in the validation strip
  let cur = null;
  const DIRECTIVES = new Set(["cancel","withdraw","new","notentered","prior"]);

  for (const raw of text.split(/\r?\n/)) {
    if (/^\s*;;/.test(raw)) {               // note line: never claim body, anywhere in the block
      notes.push(raw.replace(/^\s*;;\s?/, ""));
      continue;
    }
    const headerMatch = raw.match(/^\s*%%\s+(\d+)\s*(.*)$/);
    if (headerMatch) {
      cur = { num: parseInt(headerMatch[1], 10), rawOp: "none", priorAltered: false, paras: [] };
      for (const tok of headerMatch[2].trim().split(/\s+/).filter(Boolean)) {
        if (!DIRECTIVES.has(tok)) { /* push a validation warning: unknown directive */ continue; }
        if (tok === "prior") cur.priorAltered = true;
        else cur.rawOp = tok;              // cancel | withdraw | new | notentered
      }
      claims.push(cur);
      continue;
    }
    if (cur && raw.trim() !== "") cur.paras.push(tokenizeBody(raw));
  }

  for (const c of claims) {
    c.hasEdits = c.paras.some(p => p.some(t => t.op !== "keep"));
    if (c.rawOp === "none" && c.hasEdits) c.op = "amend"; else c.op = c.rawOp;
    Object.assign(c, computeStatus(c));   // sets status, boldLabel, keepBody
    if (!c.keepBody) c.paras = [];        // canceled: drop body
  }
  return { claims, notes };  // callers: .claims for rendering/ranges, .notes for the validation strip
}
```

### 5.4 Listing renderer (model → OOXML string), using existing `para()` / `run()` / `tab()`

```js
function renderClaimsListing(claims, claimStyle /* the style id used by the current claims path */) {
  const out = [];
  for (const c of claims) {
    const label = run("(" + c.status + ")", { b: c.boldLabel });
    if (!c.keepBody) {                                   // Canceled
      out.push(para(claimStyle, run(c.num + ".") + tab() + label));
      continue;
    }
    const firstBody = (c.paras[0] || []).map(tokenRun).join("");
    out.push(para(claimStyle, run(c.num + ".") + tab() + label + run(" ") + firstBody));
    for (let i = 1; i < c.paras.length; i++) {
      out.push(para(claimStyle, c.paras[i].map(tokenRun).join("")));
    }
  }
  return out.join("");
}
```

### 5.5 Status-of-the-Claims auto-fill (model → `st*` fields, manual override retained)

Suggested fills; leave every field editable so the attorney can adjust the status-paragraph
grammar. Use a range compressor (`[1,2,3,5] → "1-3, 5"`).

```js
function deriveStatusRanges(claims) {
  const by = s => claims.filter(c => c.status === s).map(c => c.num);
  return {
    stAmend: compressRanges(by("Currently Amended")),
    stCanx:  compressRanges(by("Canceled")),
    stAdd:   compressRanges(by("New")),
    stWd:    compressRanges(by("Withdrawn")),
    // pending = everything that still has a body (not Canceled, not Not Entered)
    stPend:  compressRanges(claims.filter(c => c.keepBody && c.status !== "Not Entered").map(c => c.num)),
    // stPrev (previously pending) and stInd (independent claims) are not derivable from status
    // alone — pre-fill stPrev with all non-New claim numbers as a suggestion; leave stInd manual.
    stPrev:  compressRanges(claims.filter(c => c.status !== "New").map(c => c.num)),
  };
  // Do NOT overwrite stInd or stSupport.
}
```

## 7. UI additions (Claims Builder panel)

Add one fieldset, styled with the existing classes (`fieldset`, `fs-head`, `fs-body`, `field`,
`toggle`, `mini-legend`, etc. — match the current look; introduce no new visual language).

- **Source textarea** `#ixSource` — the interchange block (monospace). Placeholder shows a two-claim
  example and the markup legend.
- **Live preview** `#ixPreview` — on input, parse and render a read-only preview: for each claim,
  `N. (Computed Label)` with the label bold when applicable, insertions shown underlined, deletions
  shown struck, `[[ ]]` shown literally. This is the attorney's confidence check before generating.
- **Validation strip** `#ixValidate` — surface, without blocking:
  - unbalanced markup delimiters (`{+` without `+}`, `[-` without `-]`, `[[` without `]]`) — error;
  - duplicate claim numbers — error;
  - `new` combined with `prior` — warning (contradiction);
  - a claim carrying body text under `cancel` — warning (body will be dropped);
  - unknown directive tokens — warning;
  - any manual `st*` override that disagrees with the derived ranges — warning.
- **Reasoner notes.** Lines beginning with `;;` are notes, not claim text. The parser strips them
  (see §5.3, `notes[]`) and never treats them as claim body, wherever they appear in the block.
  Display them verbatim in `#ixValidate` under a "Reasoner notes" heading. The antecedent-basis
  scan is **not** the tool's job — display pass-through notes only; do not compute them.

Keep the existing `claimsText` textarea as a labeled fallback ("verbatim paste — bypasses the
Claims Builder") so nothing regresses.
